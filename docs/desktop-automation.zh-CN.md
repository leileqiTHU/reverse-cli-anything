# 没有公开 API，如何自动化闭源桌面软件

[English](desktop-automation.md) · [reverse-cli-anything](../README.zh-CN.md) · [原生自动化案例](native-automation-examples.zh-CN.md)

当 AI Agent 需要修改文档、调整 CAD 参数或导出视频，而软件没有合适的公开 API 时，**reverse-cli-anything** 帮助编程 Agent 研究缺失操作，通过分析发行产物和运行时建立经过验证的 CLI。交付物是可复用的任务工具；新软件是否支持，需要实际研究和验收。

## 谁会需要这套框架？

- **Agent 开发者和自动化工程师：** Agent 能运行命令，但桌面应用没有开放所需操作。
- **创作与工程软件用户：** 需要保留可编辑的原生工程，使用软件自身生成结果，并通过对话重复执行工作流。
- **逆向工程开发者：** 已找到内部函数或命令，需要明确调用约定、会话、状态与验证方法，才能交付可用接口。
- **工具维护者：** 软件升级导致适配器失效，或者需要让另一个 Agent 接续已有研究。

## 选择自动化路线

| 路线 | 适用情形 | 需要验证什么 |
| --- | --- | --- |
| 公开 CLI、SDK、脚本 API 或现有 MCP 工具 | 已开放所需操作。 | 操作覆盖、支持版本和实际输出，应优先检查。 |
| 项目文件编辑 | 工作目标可以通过已理解的文件格式表达。 | 软件能否正确打开、保留可编辑性并渲染结果；写入 JSON 本身不能证明控制了实时编辑器。 |
| GUI 自动化或 RPA | 工作流程可通过用户界面执行。 | 焦点、弹窗、时序，以及软件是否真的保存或导出结果。 |
| 逆向恢复原生控制 | 公开接口不足，且可通过研究恢复内部业务操作。 | ABI、线程、对象生命周期、活动项目与会话、版本身份和完整流程结果；这是本框架的主要工程用途。 |

一个流程可以组合多条路线。原生控制不等于无头运行：CapCut 案例需要应用进程和活动编辑会话。CLI 使用 JSON 输入输出，只说明其对外契约，不能据此判断底层是在编辑文件还是调用软件。

## 如何让 AI Agent 为新软件建立 CLI？

先使用[安装提示词](../README.zh-CN.md#最简安装复制给你的-agent)，再描述需要交付的原生结果：

```text
用 reverse-cli-anything 为 <软件与版本> 构建 CLI。
我需要打开 <输入>，完成 <具体编辑>，保存可编辑的原生项目，
并导出 <格式>。先检查公开接口，再研究缺失能力，
在真实软件中验证完整流程，并按需验证保存后重新打开。
```

Agent 应先明确操作缺口和目标版本，再按原生二进制、托管程序集、嵌入脚本或协议选择分析工具，恢复有明确边界的调用契约，验证单项操作，再扩展完整流程。[工程手册](HARNESS.zh-CN.md)说明具体方法，[初步调查指南](guides/reconnaissance.zh-CN.md)说明研究路线选择。

## 找到内部函数后，怎样变成可靠工具？

函数地址只是起点。封装还必须明确调用对象、执行线程、参数单位、所有权和完成信号。修改操作需要核对原生状态，以及保存或导出的产物；交付时保留目标版本、证据和恢复说明。

框架提供[适配器契约](adapter-contract.zh-CN.md)、[结构化调用和回执](runtime.zh-CN.md)、[交付指南](guides/delivery.zh-CN.md)。MCP 集成可以调用交付的 CLI，但本框架不宣称为任意目标自动生成现成 MCP 服务。

## 软件升级后，CLI 怎么维护？

内部接口可能随版本变化。需要重新检查版本身份、定位变化入口，并对受影响工作流重新验收，才能声称兼容。参见[版本升级流程](workflows.zh-CN.md)和[状态恢复指南](guides/state-and-recovery.zh-CN.md)。某个版本可用，不代表其他版本自动兼容。
